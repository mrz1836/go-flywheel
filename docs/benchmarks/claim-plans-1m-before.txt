notes
  - Rows are spread evenly across 4 executor classes (loadtest, (empty wildcard), loadtest-b, loadtest-c), so a routed
    claim matches half the table. A seed in which every row matched would flatter any variant that drops the class
    from the key.
  - Every row is claimable: state='available', deleted_at IS NULL, scheduled_at in the past. The claim's LIMIT is 8,
    so any Sort over more than 8 rows is work the plan did not need to do.
  - Conditions E and F name "q-idle", which the seed never writes to, so they measure an empty poll. That is the case
    a deployment spends most of its wall clock in — a runner polls on a fixed interval whether or not there is work
    — and an index that answers a hit quickly and a miss slowly would be worse than the one it replaced.
  - Every statement was captured from postgresDriver.Dequeue through a recording GORM logger and explained verbatim;
    P1 differs from P0 by exactly one documented Replace of the class clause.
  - EXPLAIN (ANALYZE) executes the claim, so every capture ran inside a transaction that was rolled back. The seeded
    table is identical for every cell.
